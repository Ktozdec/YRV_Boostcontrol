# Прошивка ESP32 — YRV_Boostcontrol

Прошивка контроллера наддува для Daihatsu YRV Turbo (K3-VET). Два варианта:

```
firmware/boost_controller_refined/boost_controller_refined.ino        # V1 — базовая (ручные kP/kI/kD)
firmware/boost_controller_refined_v2/boost_controller_refined_v2.ino  # V2 — самонастраивающийся ПИД
```

V2 — это V1 плюс **самонастройка коэффициентов ПИД** (см. раздел
[Самонастраивающийся ПИД (V2)](#самонастраивающийся-пид-v2)) **и переработанный BLE**: стек
**NimBLE-Arduino** вместо Bluedroid, настройки шлются серией пакетов (устойчивость к потере notify),
пакетная запись `SETALL` и разбор команд вне BLE-колбэка (очередь). Файлы независимы, **V1 не тронут**
(остаётся на Bluedroid). NVS совместим, возврат на V1 безопасен.

Общее описание системы и настройка из приложения — в корневом [README.md](../README.md).
Здесь — техническая сторона прошивки: что делает каждая задача, распиновка, тюнинг-константы,
таблица NVS и порядок прошивки.

## Что делает прошивка

- управляет соленоидом буст-контроля по **ПИД** (gain scheduling, setpoint feed-forward, анти-windup);
- ведёт **2D-карту базового duty** (TPS × RPM) с адаптивным самообучением и метрикой доверия;
- **open-loop раздув (spool assist):** высокий открытый duty (до 95 %) на спуле с плавным
  переходом к ПИД у цели; установившийся потолок duty — **85 %**;
- читает **MAP/TPS** через ADS1115, считает **RPM** (прерывание) и **скорость** (PCNT по VSS);
- **«обманка по бусту» (FCD):** ограничивает сигнал MAP, уходящий в штатный ЭБУ, через ЦАП MCP4725;
- защищает мотор режимами **SOFT_LIMP / HARD_LIMP**;
- отдаёт телеметрию по **BLE** (`YRV_Boost_BLE`) и принимает команды из Android-приложения;
- слушает **K-Line** (listen-only) и шлёт ручные HEX-запросы по команде из приложения;
- считает **одометр и моточасы**;
- сохраняет параметры, карту и одометр в **NVS**;
- поддерживает **OTA** через Wi-Fi AP `YRV_Boost_Pro`;
- защищён **watchdog**'ом; общие данные — под мьютексами.

## Структура задач (FreeRTOS)

Прошивка многозадачная, задачи закреплены за ядрами ESP32:

| Задача | Ядро | Период | Что делает |
|---|---|---|---|
| `TaskSensors` | 0 | ~10 мс | Читает ADS1115 (MAP/TPS), считает RPM (медиана 5) и скорость, пишет обманку MAP в ЦАП. |
| `TaskControl` | 1 | 50 мс (20 Гц) | Главный контур: карта + ПИД + раздув + защита, slew-лимит, запись ШИМ соленоида, обучение карты. |
| `TaskTelemetry` | 1 | ~40 мс | Шлёт телеметрию/настройки по BLE, печатает диагностику в Serial. |
| `TaskKLineReader` | 0 | ~2 мс | Сниффер K-Line: собирает кадры по тайм-ауту между байтами. |
| `TaskOdometerAndStorage` | 0 | по событию | Копит одометр/моточасы, пишет настройки/карту/одометр в NVS с защитой от частых записей. |
| `TaskBleCommands` (V2) | 0 | по событию | Разбирает команды приложения вне BLE-колбэка через очередь: `GET:SETTINGS`/`SET`/`SETALL`/`SAVE`/`DUTY`/`RESET`/`KREQ`/`OTA`. |

> Период контура — **50 мс**. 10 мс (100 Гц) «голодал» программный ISR тахометра и RPM читался
> вдвое меньше — поэтому 50 мс трогать не нужно.

## Контур управления duty

В `TaskControl` каждый цикл:

```
base      = карта duty по (RPM, TPS)               // самообучаемая база
target    = tB × форма_по_RPM, сглаженная фильтром  // цель буста
err       = target − boost

kP,kI,kD  = базовые усиления × gain scheduling(RPM)  // агрессивнее на спуле, мягче вверху
dutyPID   = base + kP·err + ∫kI·err + kD·d(boost) + setpointFF   // с анти-windup (back-calc)
dutyPID   = clamp(dutyPID, 0..85%)

blend     = насколько мы ниже цели (между bL и bH)   // 0..1, с одноразовой защёлкой-латчем
dutyOut   = max(dutyPID, смесь(dutyPID, 95%, blend)) // раздув только добавляет, не убавляет

// soft limp прижимает dutyOut пропорционально превышению; hard limp = 0
dutyOut   = slew(dutyOut)  // вверх быстро (800 %/с), вниз — cfg.dutyFallSlewPerS
ledcWrite(соленоид, dutyOut)
```

**Самообучение карты.** Когда режим устойчив (см. окно `LEARN_*`), установившаяся часть
интеграла переносится в окрестные ячейки карты (LMS-шаг по билинейным весам), а интеграл на ту
же величину разгружается. Так база со временем «запоминает» нужный duty, а ПИД остаётся
свободным для переходных режимов.

## Режимы защиты

`updateSafety()` каждый цикл выставляет режим:

| Режим | Условие | Реакция |
|---|---|---|
| `NORMAL` | всё в норме | штатное регулирование |
| `SOFT_LIMP` | `boost > softLimpBar` | duty прижимается пропорционально превышению (квадратичный bleed), ПИД продолжает работать |
| `HARD_LIMP` | `boost > hardLimpBar`, либо MAP/TPS вне `0.1–4.9 В`, либо обороты есть без датчика | duty мгновенно 0, slew в обход |

Пороги **производные от цели** и пересчитываются `recomputeLimpThresholdsLocked()`:
**`softLimpBar = targetBoost + 0.15`**, **`hardLimpBar = targetBoost + 0.20`**. Отдельно их
задать нельзя — меняется только цель `tB`, пороги следуют за ней (на загрузке и при каждом
`SET:tB`). Ключи `sL`/`hL` принимаются для совместимости, но значение игнорируется.

## Распиновка

| Пин | Назначение |
|---|---|
| `25` | ШИМ соленоида (30 Гц) |
| `18` | Тахо (RPM, прерывание) |
| `19` | VSS (скорость, PCNT) |
| `23 / 22` | I²C SDA / SCL (ADS1115 + MCP4725) |
| `16 / 17` | K-Line RX / TX (Serial2, 10400 бод) |

Адреса I²C: **ADS1115 `0x48`**, **MCP4725 `0x60`**. Шина на **100 кГц** (400 кГц через
логический преобразователь портили чтение ADS1115).

## Блок тюнинг-констант (ADAPTIVE TUNING)

Все «ручки» собраны в начале `.ino` в блоке `ADAPTIVE TUNING`. Это **power-on значения по
умолчанию** — сохранённое в NVS значение их переопределяет (кроме случаев миграции, см. ниже).

**Базовый ПИД (актуальный тюн):**

| Константа | Значение | Смысл |
|---|---|---|
| `DEFAULT_KP` | **20.0** | пропорциональное усиление |
| `DEFAULT_KI` | **14.0** | интегральное усиление |
| `DEFAULT_KD` | **8.0** | дифференциальное усиление |
| `DEFAULT_LEARN_RATE` | 0.10 | скорость обучения карты (`lA`) |

**Раздув (spool assist):**

| Константа | Значение | Смысл |
|---|---|---|
| `SPOOL_DUTY_MAX` | 95.0 % | потолок duty **только на раздуве** (не сустейн!) |
| `DUTY_RISE_SLEW_PER_S` | 800 %/с | скорость нарастания duty (чтобы не душить спул) |
| `SPOOL_BLEND_HIGH_DEF` | **0.15 бар** | дефицит для полного раздува (`bH`) |
| `SPOOL_BLEND_LOW_DEF` | **0.03 бар** | дефицит окончания раздува (`bL`) |
| `DUTY_FALL_SLEW_DEF` | **150 %/с** | скорость спуска duty (`fS`) |

**Потолки и защита:** `MAP_DUTY_MAX` = 85 % (установившийся потолок). Пороги limp производные от
цели: `SOFT_LIMP_TARGET_OFFSET` = 0.15 и `HARD_LIMP_TARGET_OFFSET` = 0.20 — это запас над `tB`
(soft = target + 0.15, hard = target + 0.20), не отдельные настройки.

> ⚠️ `MAP_DUTY_MAX` (85 %) поднимать нельзя — соленоид перегревается/подвисает, если держать выше
> ~85 % длительно. 95 % допустимы лишь кратковременным импульсом раздува.

## Хранение в NVS и миграции

Параметры, карта и одометр хранятся в NVS (namespace `yrv_v4`). Ключи `SET` из приложения
(`tB`, `kP`, `bH`, …) — это же ключи в NVS.

**Версионирование тюна (`tuneVer`)** форсирует обновлённые значения один раз поверх стейла:

| Версия | Что делает |
|---|---|
| `< 6` | форсит ПИД-усиления и калибровки датчиков (oP/sP/oV) на дефолты v6 |
| `< 7` | сбрасывает старую карту/доверие — `loadMap()` строит карту из новых дефолтов |
| `< 8` | форсит новый базовый тюн: ПИД `kP=20 / kI=14 / kD=8` и раздув `bH=0.15 / bL=0.03 / fS=150` |

Поэтому новые базовые значения становятся активны **после прошивки автоматически**, без ручного
сброса. Дальше приложение может донастраивать их, и правки сохраняются.

## Самонастраивающийся ПИД (V2)

Только в `boost_controller_refined_v2/`. Идея: карта duty уже снимает **установившийся** режим,
значит ПИД отвечает за **переходный процесс**. Тюнер оценивает каждый разгон («эпизод») и делает
**один маленький ограниченный шаг** по коэффициентам — та же логика «сходимся за десятки пуллов»,
что и у обучения карты.

**Отдельные ключи.** Авто-усиления живут в своих NVS-ключах **`kPa` / `kIa` / `kDa`**, контур V2
считает duty по ним. Ручные `kP/kI/kD` (V1) — только сид: при первой прошивке V2 (`tuneVerV2 < 1`)
`kPa/kIa/kDa` инициализируются из них. Возврат на V1 → едет на ручных, ничего не затёрто.

**Эпизод.** Открывается на настоящем тип-ине (защёлка раздува + дефицит > `bH` + гейтинг по
TPS/RPM/скорости), закрывается по «успокоению» (`|err| < 0.03` бар держится `AT_SETTLE_HOLD_MS`)
или по тайм-ауту. Метрики: перерегулирование, время нарастания, число автоколебаний, факт limp.

**Закон (один доминирующий симптом за эпизод):**

| Симптом | Действие |
|---|---|
| овербуст (HARD_LIMP / `peak ≥ hardLimpBar`) | **паник-детюн**: `kPa −12 %`, `kIa −15 %` |
| хантинг (смен знака > `AT_OSC_MAX`) | `kPa ↓`, `kIa ↓` |
| перерегулирование > `AT_OVERSHOOT_HI` | `kPa ↓`, `kDa ↑` |
| вяло (rise долгий, переброса нет) | `kPa ↑` |
| остаточный сдвиг > `AT_OFFSET_HI` | `kIa ↑` |

**Защита:** жёсткий envelope `KP/KI/KD_MIN..MAX` (выйти нельзя), асимметрия (вниз быстро, вверх
медленно), watchdog-откат к last-known-good при росте перерегулирования, EWMA-сглаживание метрик,
заморозка в limp. Все пороги — в блоке `V2: SELF-TUNING PID` в начале `.ino`.

**Управление и телеметрия.** Рантайм-ключ **`aT`** (`SET:aT:0/1`) — вкл/выкл тюнера. Живые
`kPa/kIa/kDa` и счётчик эпизодов `ate` шлются в пакете телеметрии `T`; флаг `aT` — в пакете
настроек `S`. В приложении: карточка «ПИД-регулятор и обучение» → блок **Автотюн ПИД (V2)**
(индикатор живых усилений + кнопка вкл/выкл). Ручная правка `kP/kI/kD` в V2 **ре-сидит**
соответствующее авто-усиление («тюнить отсюда»), так что слайдеры остаются рабочими.

**NVS-миграция V2** — отдельный ключ `tuneVerV2`, не пересекается с `tuneVer`:

| Версия | Что делает |
|---|---|
| `< 1` | сид `kPa/kIa/kDa` из `kP/kI/kD`, `aT = вкл` |

В Serial раз в эпизод печатается строка `AT ep#N ovs:… rise:… osc:… -> kP:… kI:… kD:…` (метка
`PANIC` при детюне) — по ней видно сходимость.

## Прошивка и первый запуск

Перед прошивкой проверьте:

- выбрана правильная плата ESP32 и установлены все библиотеки;
- пины соответствуют реальному подключению (см. `docs/hardware/`);
- адреса I²C: ADS1115 `0x48`, MCP4725 `0x60`.

При первом запуске **MAP авто-зануляется на атмосфере** (усреднение 10 отсчётов, если среднее в
окне `2.40–2.70 В`). Если в этот момент не атмосферное давление (например, перезагрузка на ходу),
авто-зеро пропускается и берётся сохранённая калибровка — это безопасно.

Обновление по воздуху: команда `OTA:ON` из приложения → плата поднимает Wi-Fi AP
`YRV_Boost_Pro` → откройте `http://192.168.4.1` и загрузите `.bin`.

## Диагностика по Serial

На `115200` бод раз в ~5 с печатаются строки:

- `Diag` — свободная память, режим, BLE MTU/подключение;
- `Sensors` — вольты MAP/TPS, буст, RPM, TPS, скорость, счётчик отказов АЦП (`ADCfail`);
- `ADC` — статус по каналам (ch0=MAP, ch1=TPS) и состояние ЦАП;
- `RPMraw` — период между фронтами тахо и счётчик фронтов;
- `KLINE` — счётчики байт/кадров/переполнений сниффера.

> `ADCfail > 0` означает потерю связи с ADS1115 по I²C (а не «0 В на входе»).

> (V2) Этот 5-секундный блок обёрнут в `#define DEBUG_DIAG` — поставьте `0` для релизной сборки,
> чтобы не тратить такты на печать.
